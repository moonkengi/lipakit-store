# 08 · Failure modes

Every M-Pesa integration eventually meets each of these. This is what happens and what the kit does about it. Each one has a simulator scenario and a test.

| What goes wrong                                       | Why it happens                                                       | What the kit does                                                                                                                            | Try it                                         |
| ----------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **The callback never arrives**                        | Network blips, your server redeploying, Daraja having a bad day      | The poller STK-queries every push still pending after 60 s and settles it                                                                    | Simulator: missing callback                    |
| **The callback arrives late**                         | Delivery delayed past the poller's check                             | The poller settles first; the late callback only fills in the receipt number                                                                 | Simulator: late callback                       |
| **The callback arrives twice**                        | Daraja retries                                                       | Only a pending transaction can settle, enforced in Postgres under a row lock; the second is a no-op                                          | Simulator: duplicate callback                  |
| **A fake callback**                                   | Callback URLs are unsigned; anyone who learns the URL can POST to it | The URL holds a secret token, and **no callback is trusted on its own**: every result, success or failure, is confirmed with STK Query first | `tests/reconcile/stk.test.ts` "forged success" |
| **The callback and the poller race**                  | Both arrive at the same moment                                       | Row lock + "only if pending": exactly one settles                                                                                            | `tests/reconcile/stk.test.ts` "race-safe"      |
| **Paid a different amount**                           | Usually a forged or altered callback (STK amounts are set by you)    | Order goes to **Needs review**; a human decides                                                                                              | Simulator: amount mismatch                     |
| **"Still processing"**                                | The customer hasn't finished; STK Query answers with an error code   | Treated as pending, not as a failure                                                                                                         | `tests/mpesa/client.test.ts`                   |
| **Phone off or unreachable**                          | No network, phone locked                                             | Result 1037: order expires with a helpful message; the customer retries                                                                      | Simulator: timeout                             |
| **Wrong PIN, cancelled, insufficient funds**          | Customers being customers                                            | Clear message per result code; retrying creates a fresh order                                                                                | Simulator outcomes                             |
| **No answer at all for 10 minutes**                   | The push got lost somewhere                                          | The poller expires it, so nothing is "pending" forever                                                                                       | `tests/reconcile/stk.test.ts`                  |
| **Paybill payment with a typo in the account number** | People type account numbers by hand                                  | Match by phone + exact amount (if exactly one order fits), else the **Unmatched** queue for manual assignment                                | Simulator: Paybill payment                     |
| **Paid via STK and via Paybill**                      | Paybills with C2B URLs also send a C2B confirmation for STK payments | Same M-Pesa receipt, so whichever arrives first settles and the other is a no-op                                                             | `tests/sql/billing.sql` case 11                |
| **Paid an already-paid bill**                         | Customer pays a reminder they'd already paid                         | Lands in **Unmatched** as a possible double payment                                                                                          | `tests/sql/billing.sql` case 9                 |
| **Ratiba payment doesn't come**                       | Standing order cancelled, or not enough balance                      | At period end the plan falls back to reminders + grace; access isn't cut without warning                                                     | `tests/billing/renewals.test.ts`               |
| **Payout with no clear answer**                       | Network error or queue timeout on B2C                                | Marked **unconfirmed**, never "failed", and nothing resends automatically: money may have moved. Check the statement                         | Simulator: timeout, on a payout                |
| **Double-clicked "Send payout"**                      | Humans                                                               | Idempotency key per form: the second submit returns the first payout                                                                         | `tests/sql/admin.sql` case 4                   |
| **Scheduler silently stopped**                        | Cron misconfigured after a domain change                             | Every job run is recorded; Health shows "looks stopped"                                                                                      | Health page                                    |
| **Callback processing crashed**                       | A bug, or a bad deploy                                               | The raw payload was stored before processing; fix, then **Replay** from the callback log                                                     | `/admin/callbacks`                             |
| **Callback URL rejected at registration**             | It contains a word Safaricom blocks                                  | The kit refuses before calling Daraja, naming the word                                                                                       | `tests/mpesa/c2b-ratiba.test.ts`               |
